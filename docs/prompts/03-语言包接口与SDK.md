# 阶段 3 提示词：Language Pack API v1、SDK 与示例包

请执行本阶段，并遵守 `docs/prompts/00-共同约束.md`。依赖阶段 2 的双应用工程。目标是公开一个第三方可以实现和验证的 Android 语言包接口；不要把 JSON 清单当成完成的插件机制。

## 架构选择

- 可执行语言包采用**单独安装的 Android APK**，包内自带与其能力对应的 Android 版解释器、编译器或分析器。IDE 与语言包通过版本化的显式服务接口通信；优先制作 AIDL 原型，并用设备实测确认跨应用发现、绑定和权限行为。
- 语法主题、关键字与代码片段可采用无可执行代码的资源包；资源包与可执行包在 UI 中标明不同能力级别。
- GitHub 静态索引仅提供元数据和 Release 链接，不作为运行时权限来源。用户明确安装 APK 后，IDE 校验包名、签名指纹、协议版本、ABI 和声明能力，再提供使用入口。记录第三方包风险与撤销／禁用方式。

## 必须制定的 API

1. 包内清单：`schemaVersion`、`packId`、`version`、`minHostVersion`、`minSdk`、`supportedAbis`、`languageIds`、扩展名、能力、入口服务、来源、许可证和依赖。GitHub 静态索引另列发布后才能确定的 APK SHA-256 与签名证书指纹，避免包内文件自引用哈希。给出两种清单的 JSON Schema 和有效／无效示例。
2. 任务：`initialize`、`analyze`、`complete`、`build`、`run`、`cancel`、`diagnostics`。每个请求带唯一任务 ID、版本和工作区范围；结果带状态、源码位置、退出码及可显示错误。大文件和输出用流／文件描述符，避免 Binder 大对象限制。
3. 文件：由 IDE 掌握 SAF 权限，向语言包传入受控的只读输入或任务运行副本；需要写回时走显式结果清单与冲突确认。不得要求语言包直接解释任意 `content://` URI 为文件路径。
4. 生命周期：前台任务、取消、超时、服务崩溃、包卸载、版本不兼容、后台限制和日志保留。明确哪些能力是 v1 必须实现，哪些为可选。
5. 补全／诊断采用清楚的源码位置与编码约定，并在适合处复用 LSP 语义；为后续 DAP 调试保留能力槽，但 v1 不声称已支持调试。

## 交付物

- `docs/language-pack-api/v1/`：规范、Schema、错误码、生命周期图、权限与安全模型、版本兼容策略、静态索引格式。
- 可供外部开发者引用的 SDK，以及一个**不依赖大型工具链**的示例语言包 APK。
- 自动兼容性验证器：正常请求、取消、大输出、错误位置、权限拒绝、进程崩溃和版本不兼容。
- `docs/language-pack-api/v1/AI-PROMPT.md`：以 `docs/prompts/10-第三方语言包制包模板.md` 为起点，填入正式 API v1 字段、SDK 与测试命令，成为面向第三方用户的完整制包提示词。要求 AI 核对 Android 原生依赖、提交源码与可复现构建、附许可证／哈希／真实测试结果，未实现能力必须声明不可用。

## 验收

- 外部示例包可在 ARM64 实机被发现、启用、调用、取消、禁用；卸载后 IDE 正常恢复。
- 验证器能对每项声明能力做最小实测，未通过的能力不得在 IDE 中显示为可用；错误可追溯到包和任务。
- 规范足以让未参与本工程的开发者从零写出兼容示例，不需要改 IDE 主体源码。
